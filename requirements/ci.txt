# Dependabot's pip fetcher reads THIS file and nothing else under requirements/
# (every other manifest is excluded -- see .github/dependabot.yml). Its
# `requirements_file?` check accepts a .txt only if EVERY line is blank, a
# comment, a `-r`/`-c`/`-e`/`--` directive, or a parseable requirement. One
# unparseable line rejects the whole file, and with no candidate left the
# fetcher aborts "No files found in /requirements" and CLOSES the open update
# PRs as though the dependency had vanished. That is what happened to #204 and
# #205. So: no PEP 508 direct references (`name @ git+...`) in this file.
# tests/platform/test_dependabot_scope.py enforces it.
#
# The line that tripped it was a torchtune requirement, removed here because CI
# does not use torchtune at all. Only src/training/trainer_grpo.py imports it
# (`from torchtune.dev.rl.loss import GRPOSimpleLoss`), nothing imports THAT
# module except a deferred import inside src/train.py, and no test touches
# either. Verified by making torchtune unimportable and re-running every CI
# command: all four pytest jobs collect and pass identically, and `mypy src` is
# unaffected (torchtune ships no py.typed, so mypy already resolved
# GRPOSimpleLoss to Any with the package installed -- `ignore_missing_imports`
# does the same without it). Aurora and Polaris still get torchtune; both
# requirements/base.txt and requirements/polaris.txt document the clone-and-
# install-editable step, which is where a git dependency belongs.
#
# torchao, by contrast, IS required: without it 26 test modules fail to collect,
# because transformers 4.57.6 imports quantizers/quantizer_torchao.py eagerly.
# CI's window is narrower than the HPC manifests', so this pin deliberately
# DIFFERS from the 0.5.0 in requirements/base.txt and requirements/polaris.txt:
#
#   >= 0.9.0    transformers 4.57.6 reads torchao.quantization.Float8WeightOnlyConfig
#               at import time (quantizers/quantizer_torchao.py, guarded only by
#               `is_torchao_available()`, whose floor is 0.4.0 -- so an older
#               torchao raises AttributeError there and every `from transformers
#               import X` surfaces as a misleading "cannot import name 'X'").
#               transformers 5.x does not touch it, which is why 0.5.0 worked
#               while this file floated transformers.
#   <  0.18.0   removes torchao.dtypes.nf4tensor. Nothing in CI imports that
#               symbol now that torchtune is gone, but Aurora's torchtune fork
#               does at package-init time, and keeping CI inside the cluster's
#               window is the point of pinning to what Aurora ships.
#
# Both bounds were bisected on py3.10, not guessed: 0.8.0 lacks the symbol and
# 0.9.0 is the first release to carry it. 0.15.0 sits inside the window and is
# what Aurora's frameworks/2025.3.1 ships beside transformers 4.57.6, so CI and
# the cluster agree rather than merely both working.
torchao==0.15.0
